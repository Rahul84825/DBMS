# Smart Farm DBMS — Known Limitations & System Scope

**Project:** Smart Farm Database Management System  
**Engine:** MySQL 8.x (InnoDB)  
**Document:** System Boundaries, Known Constraints, and Demonstration Scope  

---

## 1. Engine & Environment Prerequisites

1. **MySQL 8.0+ / 8.4 LTS Required:**  
   The project schema relies on features specific to MySQL 8.x:
   - **Enforced `CHECK` Constraints:** In MySQL 5.7 and earlier, `CHECK` clauses were parsed but ignored by the engine. MySQL 8.0 strictly validates data ranges.
   - **Window Functions:** Queries in `sql/03_reports.sql` utilize `ROW_NUMBER() OVER (...)` to isolate the latest telemetry readings. This syntax is unsupported on legacy MySQL versions (< 8.0).
2. **Current Local Server Inactivity:**  
   As documented in [ENVIRONMENT_AUDIT.md](file:///c:/Users/activ/OneDrive/Attachments/Desktop/DBMS-%20Project/docs/ENVIRONMENT_AUDIT.md), MySQL Server is currently not active in the local Windows environment. Live query execution will take place once the local database daemon is started.

## 2. Telemetry Simulation Boundaries

1. **Synthetic Telemetry Model:**  
   The telemetry generator (`simulator/simulate_readings.py`) produces deterministic pseudo-random values. It is designed for demonstration in MySQL Workbench without requiring physical microcontrollers, LoRaWAN gateways, or MQTT brokers.
2. **Batch SQL Generation vs. Real-Time Streaming:**  
   In this beginner-friendly mini-project, telemetry readings are ingested as batch `.sql` files generated by Python. In a production enterprise system, real-time telemetry would stream directly via an IoT broker (e.g., Eclipse Mosquitto, AWS IoT Core) into Kafka or a time-series database.
3. **Illustrative Demonstration Thresholds:**  
   The $30.00\%$ demonstration alert threshold used in queries is purely illustrative. It must not be interpreted as universal agronomic advice. In actual practice:
   - Optimal moisture thresholds depend on soil type (sand vs. clay) and crop growth stage.
   - The system serves as a **decision-support advisory**, and does **not** actuate physical valves or pumps.

---

## 3. Scope Boundaries (By Design)

In strict adherence to the project specification:
- **No Web Frontend / REST API:** The system is purposefully engineered as a pure relational database management project inspected via MySQL Workbench and the MySQL CLI.
- **No External Authentication System:** Access control relies entirely on MySQL native user privileges (`GRANT` / `REVOKE`).
- **No Cloud Services:** The project runs entirely on local workstation hardware.

---

## 4. Scalability Considerations for Future Growth

1. **Time-Series Table Partitioning:**  
   `sensor_reading` is designed as a time-series table. In a commercial farm with hundreds of sensors logging readings every 60 seconds, this table could generate millions of rows per month. A recommended future enhancement is implementing MySQL range partitioning by `recorded_at` (e.g., `PARTITION BY RANGE (TO_DAYS(recorded_at))`).
2. **Data Retention & Archiving:**  
   For production deployments, an automated scheduled event (`CREATE EVENT`) should aggregate raw minutely readings into hourly averages after 90 days to conserve storage.
